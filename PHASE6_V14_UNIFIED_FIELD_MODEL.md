# Phase 6 v14 — Unified Field Model

## Core UX rule
There is no separate concept in the Studio UI for "fields", "questions", or "decisions". A designer creates **fields**. A field can be text, long text, number, date, date/time, yes/no, single choice, multi choice, employee, organization unit, position, or user.

A field may later be referenced by a workflow condition. The condition UI is intentionally limited to:
- Field
- Value
- Effect

The default route is always the next stage; conditions exist only for exceptions.

## Requester
The transaction belongs to the requester by default. The optional **employee concerned** is represented by a normal employee field. If omitted, the backend links the transaction to the requester's employee automatically. If included and selected, the selected company employee becomes the transaction employee.

## Backward compatibility
Existing legacy workflow questions are converted in the Studio UI to fields when a workflow is opened. On save, the draft stores the unified representation in `workflow_fields`; legacy question rows are no longer generated by the Studio. Legacy question conditions are converted from `question.<key>` to `field.<key>` when loaded.

## Test environment
The isolated test flow now presents requester fields first, then the current stage fields. Answers remain available while moving through stages so later conditions can use prior data.

## Actual transaction UI
New transaction creation uses one requester-data section. The transaction detail already presents requester identity first, then requester data, current-stage data, and the single "Pass transaction" action.

## Reset
Studio reset remains A-Z for Phase 6 and clears the local test-run store as well as the Phase 6 D1 transaction/template tree. Companies, employees, users, permissions, roles, and Phase 1–5 data are preserved.
